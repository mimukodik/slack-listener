# Decisions

What each change established and why, newest last. A check can be passed by weakening it, so every change to [RULES.md](RULES.md), the simulator's checkers or the fake Slack after the first green run is logged here with its direction and cause.

## 2026-11-17: the rules

- **R12 is a loop detector, not a rate limit.** A fuse of 20 agent posts in a row in one thread, set by `agentRunCap`. It never slows a conversation; it stops only a thread where two agents answered each other 20 times without a person, and says so in the thread.
- **R14 is removed** and its id is not reused. It rationed new threads per hour; limiting the rate of communication is not the right lever.
- **Step 2 posting** goes on once step 1 has its live proof and the two-instance settling simulation passes with R12 and R13. The Slack app carries `chat:write` from the start, so it is created once; posting stays off in the configuration until then.
- **Tokens** come from 1Password with `op read`; the configuration holds `op://` references only.

## 2026-11-17: the method, and what it gave

The core is a pure `step(state, event, now)`; the shell runs its effects (Slack, timers, the session, the state file). `src/sim` runs the core against a fake Slack with seeded faults; fast-check drives the choices and shrinks failures. The safety rules are checked after every step and the progress rules at the end of each run, and two controls (a build that delivers nothing, a build that delivers everything) must fail. Beside the sampling, a bounded exhaustive pass runs every sequence of up to 7 actions over an alphabet of 8 (two thread starters, a reply in each, an edit, a disconnect, a crash, a duplicate): 87,796 sequences, no violation; up to 8 actions, 470,620 in about 37 s. A conformance test compares the fake Slack with recorded real events.

- Gave: four real core bugs found before any live run, each now a kept scenario test in `src/core.spec.ts` (an edit lost to a crash during catch-up, out-of-order release, an older edit after a newer one, a late redelivery out of order).
- Gave: one hard limit made explicit (reply edits during a gap; RULES.md, out of scope) instead of a silent gap.
- Cost: the fake Slack is a second model to keep honest; one correction before any recording (deleted thread parents stay as tombstones). Every later surprise from real Slack becomes a recorded fixture first and a change to the fake second.
- Cost: about a third of the build time went to the simulator and oracle, and one of the finds was the oracle's own bug.
- Not used: TLA+ (the fast-check model of two settling instances covers step 2's one concurrency question) and machine-checked proofs (out of proportion for this tool). Mutation checks are done by hand: each new or tightened check is shown to fail on a deliberately broken build, with counts in the pull request.

A top-level post, a thread reply and an edit each reached the receiving session once, 3 to 4 s after posting, with the right `thread_ts`. Three posts by the own side's agents, one of them the receiving session's own answer, were dropped by R10.

## 2026-11-17: Tiger Style and the whole program under simulation

[PRINCIPLES.md](PRINCIPLES.md) adopts Tiger Style and deterministic simulation testing as TigerBeetle, FoundationDB and Antithesis practise it. The aim changes: the simulator is to run the same Effect program as production and replace only the tools underneath it, not drive the core through an interpreter of its own. Three spikes showed this works with Effect 4.1.4. A seeded simulator took over Effect's scheduler, clock and randomness, and ran Effect's own HTTP client and WebSocket socket over a fake `fetch` and a fake WebSocket constructor, with hangs, network errors and crash-restarts. Every seed replayed identically, at about 0.3 ms per run, with no real timer used, and fast-check shrank a whole run's choices to a run of eleven events. Each principle states whether the code holds it today; the ones it does not are the plan.

## 2026-11-17: the simulation runtime

`src/sim/runtime.ts` is the runtime the whole program will run on: it gives Effect its scheduler, its clock and a seeded `Random`, and drives the world from one stream of choices. `src/sim/host.ts` is the simulator's only contact with the real host: it lets promise callbacks run between steps, and its tripwire makes any real timer during a run throw.

- Learned: Effect resumes a waiting fiber directly, not through the scheduler; it uses the scheduler only when a fiber has used up its turn or a forked fiber starts. A scheduler alone therefore decides almost nothing: a probe saw one ready task at every pick. The seed now decides interleaving where it happens: timers due at the same moment become ready tasks run in a seeded order, and every turn gets a seeded budget of operations, Effect's own 2048 halved up to eleven times, so a busy fiber is cut off at a point the seed picks. With every choice 0 the run is Effect's own: a test compares it with the same program on Effect's default scheduler.
- Learned: because a fiber resumes directly, a crash cannot stop it, only take away what would wake it. An answer to a request must therefore be a timer of the process that asked, so a crash drops it; a world timer, one that belongs to no process, must not wake a process. Promise callbacks run after every task, as Node drains microtasks after each macrotask, so a promise answered before a crash finishes while its process is alive. A task or timer of a crashed process stops the run.
- Learned: Effect runs a forked program synchronously up to its first wait, so the tripwire is on before the program starts.
- Limit: a crash cannot stop a fiber that something outside the runtime resumes: a world timer, or a promise settled in the same task as the crash. Its code runs, and is caught only if it then schedules a task. The fakes of step 3 answer through timers of the process that asked.
- Limit: the tripwire watches `setTimeout`, `setInterval` and `setImmediate`; `queueMicrotask`, `process.nextTick` and timers imported from `node:timers` are left to the lint bans.
- Measured: four fibers of four random sleeps each, 2000 runs in plain Node with the tripwire on and no warm-up: about 0.55 ms per run, no real timer. Running promise callbacks after every task doubled it from 0.26 ms. Seventeen planted bugs in the runtime and the host each fail a test, and lint catches `Math.random` and `setTimeout` planted in the runtime.

## 2026-11-17: the toolchain

The Slack SDK, Effect and the lint toolchain were weighed against the whole-program simulation, and the owner settled four things. The thin Slack client stays: the SDK's Socket Mode client keeps its connection alive on real timers and the global WebSocket, so it cannot run under the simulator, and the one thing it has that the client lacks, a keepalive, comes with the faults of step 4. Effect stays at the program boundary: its services are the seams the simulator replaces, and they carry over to larger applications, where patching globals in a worker does not (a database driver on raw sockets, many dependencies, several processes); the tripwire stays as the safety net. The error discipline inside Effect code comes from Effect's own rules, and oxlint and tsconfig keep it in the plain-TypeScript core. Those rules run in Effect's patched build of `tsrs` from `@effect/tsgo`, which the Effect team keeps as small patches on a pinned `tsrs`: no fork, no overlay of our own and no second type checker.

- Learned: `effect-tsgo tsrs` reports Effect's diagnostics in the type check itself, so lint runs them there; Effect's patched oxlint binding is not needed and not used. Corrected on 11-18, below: this left a second type checker.
- Learned: with all 149 Effect rules at error, today's code had 312 hits, nearly all of them preferences for Effect's own modules over native ones (`preferEffectArray` 73, `preferEffectString` 63) and `strictBooleanExpressions` 47, and none from the correctness rules. The pure core stays plain TypeScript, so those stay off. So do `extendsNativeError` (3 hits, each an error that stops the process: an assertion, the configuration, the simulator's safety check) and `preferSchemaTaggedError` (3).
- Learned: pnpm's minimum release age refused `@effect/tsgo` 0.70.0, published 20 hours earlier, and `pnpm add` wrote an exclusion for it into a new `pnpm-workspace.yaml`. The exclusion is gone; 0.69.0 with oxlint 1.93 and `tsrs` 0.25, each older than a day and supported together, are pinned instead.
- Measured: twelve new checks each fail `pnpm lint` on a planted violation: four of the nineteen Effect rules turned on (`floatingEffect`, `globalErrorInEffectFailure`, `effectTryWithoutCatch`, `tryCatchInEffectGen`), the six oxlint rules and the two tsconfig flags. The other fifteen Effect rules are on with no planted case. The twelve errors from `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes` and the nine from `promise-function-async` and `require-await` are fixed; where the flags pointed at a case that cannot happen, an assertion says so. Lint without a cache takes 0.50 to 0.56 s, against 0.38 to 0.50 s before.

## 2026-11-18: one lint pass

The setup of **2026-11-17: the toolchain** broke its own rule of no second type checker. Oxlint's type-aware rules ran on the stock `tsrs-lint` and the type check on Effect's patched `tsrs`, so lint built the program twice, on two builds of `tsrs`. `effect-tsgo --tsrs-lint oxlint --type-aware --type-check` runs oxlint's rules, the type check and Effect's rules from tsconfig.json in one pass on the patched `tsrs`. Effect calls `--tsrs-lint` experimental and oxlint calls `--type-check` experimental; the stock `tsrs-lint` it replaces was the same port of tsgolint.

- Measured: the twelve planted violations of 11-17 each fail the one pass with the same rule. Run five times in a row on 0.70.0 and oxlint 1.94, the one pass took 0.22 to 0.24 s; the two passes took 0.28 to 0.29 s after a first run of 1.11 s.
- Learned: holding at 0.69.0 was a wait, not a decision. `@effect/tsgo` 0.70.0 cleared the one-day release age on 11-18 and is pinned with oxlint 1.94, again with no exclusion; `tsrs` stays at 0.25, the one version 0.70.0 supports. A version the release age holds back is pinned once it clears.

## 2026-11-18: the shell as an Effect program

Step 2 of the plan, a restructure with no rule changed. The shell, the MCP channel server, the Slack client and the log are one Effect program that reaches the world only through services: the `Clock` for the core's time and timers, `Socket.WebSocketConstructor` for Socket Mode, `HttpClient` over `fetch` for the Web API, `FileSystem` for the state file and the recording, and `Stdio` for the session. `main.ts` is the process boundary: it reads the arguments, the configuration, the tokens and the lock file with Node, and runs the program with `NodeRuntime.runMain` on the Node layers. The simulator of step 3 can run the same program on its own layers. The determinism bans now cover the program's four files as well as the core's.

- Learned: `@effect/platform-node` brings `undici` and pnpm installs its `redis` peer. `@effect/platform-node-shared` has the `FileSystem`, `Stdio` and `runMain` the listener needs and depends only on `ws`, so it is used instead (`few-dependencies`). HTTP and the WebSocket use Effect's own `FetchHttpClient` and the global constructor, as before.
- Learned: Effect marks its platform modules unstable, and its `unstableApiUsage` rule fails every use: `HttpClient`, `Socket`, `FileSystem`, `Stdio`, `runMain` and the Node layers. The rule is off for the whole project. These services are the seams the owner chose when deciding to keep Effect at the program boundary (2026-11-17: the toolchain), `effect` is pinned exactly, and a bump is a deliberate change that lint and the tests check.
- Learned: once a socket has closed, Effect's writer waits for it to open again. Each connection carries an `ended` signal and an ack races its write against it, so an ack for a closing socket never stalls the core's loop.
- Learned: a fiber the shell forks records its failure without telling anyone; before, the same crash rejected a promise and the unhandled-rejection handler stopped the process. The shell joins its fibers, so a fiber that dies stops the listener with exit 1. Replacing a timer or a connection interrupts a fiber and is not a death.
- Learned: the Effect rules caught a `try/catch` inside a generator, an Effect missing the `WebSocketConstructor` in its type, and a `this` binding that `Effect.gen` in version 4 does not take, before any test ran.
- Differs: Effect's socket gives up an opening handshake after 10 s; the connection then counts as closed and the usual backoff reconnects. Before, a hung handshake waited for the idle reconnect. Step 4's deadlines own this limit.
- Differs: a notification counts as written once stdout accepts it, not once Node flushed it. Neither tells whether the session read it, since MCP notifications have no acknowledgement, so the delivery guarantee is unchanged.
- Differs: on a `disconnect` frame the connection closes at once with "slack asked to reconnect" as its reason; before, it waited for the close handshake and logged the close code.
- Differs: error texts come from Effect: "Transport error (POST …)" instead of "fetch failed", "BadResource: FileSystem.writeFile (…)" instead of Node's error code; a state file that is not JSON says so; a failed `--check` also logs a fatal line.
- Differs: a timer replaced while its event already waits in the queue can still reach the core once, because the stepping fiber may wait on a write in between. The core ignores a timer that no longer applies.
- Differs: log and notification writes wait for a full stderr or stdout pipe to drain, so a session that stops reading stalls the loop until it reads again.
- Differs: `runMain` would exit 130 on a signal; the teardown keeps 0 for a signal or a closed session and 1 for a failure, at once, as before. The log says "stopping: interrupted" for a signal.
- Measured: a planted `Date.now`, `setTimeout`, `fetch`, `WebSocket`, `process`, `Math.random`, `node:fs` and bare `fs` import in the program's files each fail lint. A test runs the whole shell under the real `HttpClient` and `Socket` over a scripted `fetch` and WebSocket: it connects, catches up, delivers once, acks and reconnects when Slack asks. Three more tests catch a mutant each: a reply that asks Slack for a parent the shell already delivered, a timer that is not replaced, and a dead fiber that goes unnoticed. On the real Node layers, `--demo` answers `initialize`, sends its event and exits 0 when stdin closes, also before the session initialized; SIGTERM exits 0; a missing configuration exits 1.

## 2026-11-18: the whole program in the simulated world

BER-2193 completes the structural step described above. `main.ts`, the sampled simulator and the exhaustive pass call `runListener` in `src/program.ts`: the real Slack API client, MCP channel server, saved-state reader and shell. `makeLog` also runs on the simulated stdio. Both independent core-effect interpreters are deleted. The pure core, its rules and production behavior are unchanged (`structure-and-behavior-change-apart`); the shared entry is the smallest composition already needed by three real callers (`steel-thread-first`).

- **Fake boundary:** `src/sim/world.ts` replaces only `FetchHttpClient.Fetch`, `Socket.WebSocketConstructor`, `Stdio` and `FileSystem`, below Effect's real HTTP client and socket. `SimRuntime` supplies the scheduler, clock and seeded choices. HTTP responses, socket events, stdin, stdout and disk operations answer on requesting-process timers. A crash drops those callbacks without finalizers; the next process reads the last atomic rename. The fake retains duplicate and reordered envelopes, reconnect retries, 10% failed connection attempts, flapping catch-up API failures, session-write failures, edits, broadcasts, noise and injection text. History and replies now use three-message pages and opaque cursors, so losing a page reaches R7.
- **Sleep:** a laptop sleep parks process tasks and timers while world posts continue. An overdue timer becomes runnable at wake-up. Timer cancellation uses its unique sequence number, which survives parking; a canceled callback stays canceled. One test covers overdue timers, a canceled callback and a parked ready task.
- **Observation:** the oracle reads the actual JSON-RPC notification content and metadata accepted by stdout, and the actual acknowledgements sent on each fake Slack socket. It no longer renders an ideal delivery beside the program. It checks framing, sender eligibility, duplicates, ordering, thread identity, parent quotes and secrets there; reconnect attempts are timed from the observed close/failure log, and an acknowledgement must use the socket that received its envelope. A delivery-fiber defect at stdout must stop the listener loudly, extending the existing connection-fiber test.
- **R2 identity judgment:** MCP's `edited_at` has second precision. Distinct same-text edits can therefore have the same body; body alone is not an edit identity. The observation checker uses received edit time plus received body. Edits indistinguishable in both fields cannot be distinguished at this boundary. Body line breaks are normalized as the real formatter normalizes them; injected channel tags are checked in the actual output before normalization for comparison.
- **R17 cache judgment:** the unchanged shell caches the first parent it observes in each process; parent edits do not refresh that cache. The independent observer keeps the first per-thread snapshot returned by the fake parent lookup or delivered as a top-level message, and compares the actual parent metadata with that snapshot. It also requires the positive quote for a configured, existing parent, and hides an outsider. Deleted or missing parents can be absent. Enrichment reads remain reliable: the former fake applied API failure to catch-up effects only, and never modeled parent/name/workspace lookup failures. Extending those failures, parent freshness and in-flight deadlines remain outside this structural step. The stale-cache proof substitutes another thread's cached parent, rather than changing that existing freshness policy.
- **End of a run:** terminal recovery clears transient write/API failures and lets the process run. It ends after a live socket, no pending fake I/O and 65 seconds without network/session activity, then checks progress and outstanding acknowledgements. The quiet interval exceeds the 60-second retry cap; periodic state saves and stderr do not reset it, but pending disk writes still prevent closing stdin. A one-hour limit after the final wake bounds a run that never settles. This replaces inspection of private core queues and avoids assuming that all paginated catch-up fits in a fixed 180 seconds.
- **Exhaustive judgment:** each valid prefix is replayed from a fresh program and world because live Effect fibers cannot be cloned. The alphabet and fixed four-second action spacing stay; no core state or effect is interpreted by this driver. A final disconnect is healed before terminal settling, as in the former driver's `settle`. Runtime-dependent prefix validity is reported by the external world, so sequence counts are measured again rather than copied from the old interpreter.
- **Controls and evidence:** one control suppresses observed stdout deliveries; the other presents unfiltered world messages to the same notification observer. The actual program still runs in both. Whole-program replay requires the same seed to reproduce stdout and scheduler traces, and a different seed to change the trace. Catch-rate and timing receipts belong to the exact candidate and are reported with the pull request; no local receipt proves deployment or live Slack behavior.

## 2026-11-18: a fast exhaustive pass

BER-2207. Running the whole program (BER-2193) took depth 7 from about 6 seconds to about 6 minutes on CI. The program's behaviour and the checks are unchanged (`structure-and-behavior-change-apart`); a green pass reaches the same 88,025 sequences. A red pass reports less: a run that fails before its finish reports no next actions, so nothing below a failing prefix runs. It still fails with the same first violation, but with fewer sequences and violations than main counted (a planted R10 bug at depth 4: 224 and 50 against main's 1,088 and 914).

- **The cause was waiting, not Effect.** Between simulated steps the loop waited one real `setImmediate` so promise callbacks could run, about 190 per run. A third of the runs were invalid sequences run in full and thrown away, and every run built a 20,000-entry choice tape (22% of a CI profile).
- **Synchronous drain:** the loop now runs inside one macrotask and drains promise callbacks with V8's microtask checkpoint (`src/sim/host.ts`). It starts with a self-test and refuses a real `process.nextTick`, so the drain cannot silently not drain. The natives-syntax flag stays on: V8 can flush the drain's bytecode and parse it again.
- **Only valid sequences run:** each run reports which next actions its final state allows, from one precondition table, and the pass runs only those. A spec compares the prediction with running every child up to 3 actions, and the depth-5 count is pinned at 3,065, since a wrong "invalid" would drop sequences silently.
- **Split across cores:** the main thread runs sequences shorter than 3 actions and hands the 89 subtrees below to up to 8 worker threads. Violations are sorted into single-thread visiting order; a spec compares the split result with the single-threaded one, and a worker that dies or throws fails the pass by name. A worker that stays alive and never answers would hang the pass until CI's job timeout; the pool has no deadline of its own. No committed check covers the merge and sort of violations, since the parity spec's tree has none; a planted mutation showed the spec fails without the sort.
- **Not taken:** copying state at branch points. Process fork works on macOS and Linux but costs 4-14 ms against a 0.5-2.9 ms replay; a run's fixed cost (about 1 ms of start, finish and checks against 0.15 ms per action) means even a free snapshot saves less than half. Skipping repeated states and commuting orderings is the larger lever and is deliberately left out while the architecture's limits are explored.
- **CI:** moved to a 4-vCPU Blacksmith runner, faster and steadier than GitHub-hosted in the bench.

| Depth 7               | main (3ee43ea) | drain + valid only | + split            |
| --------------------- | -------------- | ------------------ | ------------------ |
| Mac, 14 cores         | about 14 min   | 70.6 s             | 16.0 s (8 workers) |
| GitHub-hosted, 4 vCPU | 405 s          | 153 s              | 82 s               |
| Blacksmith, 4 vCPU    | 342 s          | 135 s              | 45-73 s            |
| Blacksmith, 2 vCPU    | 523 s          | 222 s              | about 101 s        |

The whole CI check job went from 8 minutes 40 seconds on main to between 1 minute 55 seconds and 2 minutes 44 seconds on two runs of the same runner type. The 2000-seed pass gives byte-identical traces and results to main for every seed.
