# Decisions

What each change established and why, newest last. A check can be passed by weakening it, so every change to [RULES.md](RULES.md), the simulator's checkers or the fake Slack after the first green run is logged here with its direction and cause.

## 2026-11-17: the rules

- **R12 is a loop detector, not a rate limit.** A fuse of 20 agent posts in a row in one thread, set by `agentRunCap`. It never slows a conversation; it stops only a thread where two agents answered each other 20 times without a person, and says so in the thread.
- **R14 is removed** and its id is not reused. It rationed new threads per hour; limiting the rate of communication is not the right lever.
- **Step 2 posting** goes on once step 1 has its live proof and the two-instance settling simulation passes with R12 and R13. The Slack app carries `chat:write` from the start, so it is created once; posting stays off in the configuration until then.
- **Tokens** come from 1Password with `op read`; the configuration holds `op://` references only.

## 2026-11-17: the method, and what it gave

The core is a pure `step(state, event, now)`; the shell runs its effects (Slack, timers, the session, the state file). `src/sim` runs the core against a fake Slack with seeded faults; fast-check drives the choices and shrinks failures. The safety rules are checked after every step and the progress rules at the end of each run, and two controls (a build that delivers nothing, a build that delivers everything) must fail. Beside the sampling, a bounded exhaustive pass runs every sequence of up to 7 actions over an alphabet of 8 (two thread starters, a reply in each, an edit, a disconnect, a crash, a duplicate): 87,796 sequences, no violation; up to 8 actions, 470,620 in about 37 s. A conformance test compares the fake Slack with recorded real events.

- Gave: four real core bugs found before any live run, each now a kept scenario test in `src/core.spec.ts` (an edit lost to a crash during catch-up, out-of-order release, an older edit after a newer one, a late redelivery out of order).
- Gave: one hard limit made explicit (reply edits during a gap; RULES.md, out of scope) instead of a silent gap.
- Cost: the fake Slack is a second model to keep honest; one correction before any recording (deleted thread parents stay as tombstones). Every later surprise from real Slack becomes a recorded fixture first and a change to the fake second.
- Cost: about a third of the build time went to the simulator and oracle, and one of the finds was the oracle's own bug.
- Not used: TLA+ (the fast-check model of two settling instances covers step 2's one concurrency question) and machine-checked proofs (out of proportion for this tool). Mutation checks are done by hand: each new or tightened check is shown to fail on a deliberately broken build, with counts in the pull request.

## 2026-11-17: Tiger Style and the whole program under simulation

[PRINCIPLES.md](PRINCIPLES.md) adopts Tiger Style and deterministic simulation testing as TigerBeetle, FoundationDB and Antithesis practise it. The aim changes: the simulator is to run the same Effect program as production and replace only the tools underneath it, not drive the core through an interpreter of its own. Three spikes showed this works with Effect 4.1.4. A seeded simulator took over Effect's scheduler, clock and randomness, and ran Effect's own HTTP client and WebSocket socket over a fake `fetch` and a fake WebSocket constructor, with hangs, network errors and crash-restarts. Every seed replayed identically, at about 0.3 ms per run, with no real timer used, and fast-check shrank a whole run's choices to a run of eleven events. Each principle states whether the code holds it today; the ones it does not are the plan.

## 2026-11-17: the simulation runtime

`src/sim/runtime.ts` is the runtime the whole program will run on: it gives Effect its scheduler, its clock and a seeded `Random`, and drives the world from one stream of choices. `src/sim/host.ts` is the simulator's only contact with the real host: it lets promise callbacks run between steps, and its tripwire makes any real timer during a run throw.

- Learned: Effect resumes a waiting fiber directly, not through the scheduler; it uses the scheduler only when a fiber has used up its turn or a forked fiber starts. A scheduler alone therefore decides almost nothing: a probe saw one ready task at every pick. The seed now decides interleaving where it happens: timers due at the same moment become ready tasks run in a seeded order, and every turn gets a seeded budget of operations, Effect's own 2048 halved up to eleven times, so a busy fiber is cut off at a point the seed picks. With every choice 0 the run is Effect's own: a test compares it with the same program on Effect's default scheduler.
- Learned: because a fiber resumes directly, a crash cannot stop it, only take away what would wake it. An answer to a request must therefore be a timer of the process that asked, so a crash drops it; a world timer, one that belongs to no process, must not wake a process. Promise callbacks run after every task, as Node drains microtasks after each macrotask, so a promise answered before a crash finishes while its process is alive. A task or timer of a crashed process stops the run.
- Learned: Effect runs a forked program synchronously up to its first wait, so the tripwire is on before the program starts.
- Limit: a crash cannot stop a fiber that something outside the runtime resumes: a world timer, or a promise settled in the same task as the crash. Its code runs, and is caught only if it then schedules a task. The fakes of step 3 answer through timers of the process that asked.
- Limit: the tripwire watches `setTimeout`, `setInterval` and `setImmediate`; `queueMicrotask`, `process.nextTick` and timers imported from `node:timers` are left to the lint bans.
- Measured: four fibers of four random sleeps each, 2000 runs in plain Node with the tripwire on and no warm-up: about 0.55 ms per run, no real timer. Running promise callbacks after every task doubled it from 0.26 ms. Seventeen planted bugs in the runtime and the host each fail a test, and lint catches `Math.random` and `setTimeout` planted in the runtime.

## 2026-11-17: the toolchain

The Slack SDK, Effect and the lint toolchain were weighed against the whole-program simulation, and the owner settled four things. The thin Slack client stays: the SDK's Socket Mode client keeps its connection alive on real timers and builds undici's WebSocket, so it does not run over the simulator's fakes as they are, and the one thing it has that the client lacks, a keepalive, comes with the faults of step 4. Effect stays at the program boundary: its services are the seams the simulator replaces, and they carry over to larger applications, where patching globals in a worker does not (a database driver on raw sockets, many dependencies, several processes); the tripwire stays as the safety net. The error discipline inside Effect code comes from Effect's own rules, and oxlint and tsconfig keep it in the plain-TypeScript core. Those rules run in Effect's patched build of `tsrs` from `@effect/tsgo`, which the Effect team keeps as small patches on a pinned `tsrs`: no fork, no overlay of our own and no second type checker.

- Learned: `effect-tsgo tsrs` reports Effect's diagnostics in the type check itself, so lint runs them there; Effect's patched oxlint binding is not needed and not used. Corrected on 11-18, below: this left a second type checker.
- Learned: with all 149 Effect rules at error, today's code had 312 hits, nearly all of them preferences for Effect's own modules over native ones (`preferEffectArray` 73, `preferEffectString` 63) and `strictBooleanExpressions` 47, and none from the correctness rules. The pure core stays plain TypeScript, so those stay off. So do `extendsNativeError` (3 hits, each an error that stops the process: an assertion, the configuration, the simulator's safety check) and `preferSchemaTaggedError` (3).
- Learned: pnpm's minimum release age refused `@effect/tsgo` 0.70.0, published 20 hours earlier, and `pnpm add` wrote an exclusion for it into a new `pnpm-workspace.yaml`. The exclusion is gone; 0.69.0 with oxlint 1.93 and `tsrs` 0.25, each older than a day and supported together, are pinned instead.
- Measured: twelve new checks each fail `pnpm lint` on a planted violation: four of the nineteen Effect rules turned on (`floatingEffect`, `globalErrorInEffectFailure`, `effectTryWithoutCatch`, `tryCatchInEffectGen`), the six oxlint rules and the two tsconfig flags. The other fifteen Effect rules are on with no planted case. The twelve errors from `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes` and the nine from `promise-function-async` and `require-await` are fixed; where the flags pointed at a case that cannot happen, an assertion says so. Lint without a cache takes 0.50 to 0.56 s, against 0.38 to 0.50 s before.

## 2026-11-18: the shell as an Effect program

Step 2 of the plan, a restructure with no rule changed. The shell, the MCP channel server, the Slack client and the log are one Effect program that reaches the world only through services: the `Clock` for the core's time and timers, `Socket.WebSocketConstructor` for Socket Mode, `HttpClient` over `fetch` for the Web API, `FileSystem` for the state file and the recording, and `Stdio` for the session. `main.ts` is the process boundary: it reads the arguments, the configuration, the tokens and the lock file with Node, and runs the program with `NodeRuntime.runMain` on the Node layers. The simulator of step 3 can run the same program on its own layers. The determinism bans now cover the program's four files as well as the core's.

- Learned: `@effect/platform-node` brings `undici` and pnpm installs its `redis` peer. `@effect/platform-node-shared` has the `FileSystem`, `Stdio` and `runMain` the listener needs and depends only on `ws`, so it is used instead (`few-dependencies`). HTTP and the WebSocket use Effect's own `FetchHttpClient` and the global constructor, as before.
- Learned: Effect marks its platform modules unstable, and its `unstableApiUsage` rule fails every use: `HttpClient`, `Socket`, `FileSystem`, `Stdio`, `runMain` and the Node layers. The rule is off for the whole project. These services are the seams the owner chose when deciding to keep Effect at the program boundary (2026-11-17: the toolchain), `effect` is pinned exactly, and a bump is a deliberate change that lint and the tests check.
- Learned: once a socket has closed, Effect's writer waits for it to open again. Each connection carries an `ended` signal and an ack races its write against it, so an ack for a closing socket never stalls the core's loop.
- Learned: a fiber the shell forks records its failure without telling anyone; before, the same crash rejected a promise and the unhandled-rejection handler stopped the process. The shell joins its fibers, so a fiber that dies stops the listener with exit 1. Replacing a timer or a connection interrupts a fiber and is not a death.
- Learned: the Effect rules caught a `try/catch` inside a generator, an Effect missing the `WebSocketConstructor` in its type, and a `this` binding that `Effect.gen` in version 4 does not take, before any test ran.
- Differs: Effect's socket gives up an opening handshake after 10 s; the connection then counts as closed and the usual backoff reconnects. Before, a hung handshake waited for the idle reconnect. Step 4's deadlines own this limit.
- Differs: a notification counts as written once stdout accepts it, not once Node flushed it. Neither tells whether the session read it, since MCP notifications have no acknowledgement, so the delivery guarantee is unchanged.
- Differs: on a `disconnect` frame the connection closes at once with "slack asked to reconnect" as its reason; before, it waited for the close handshake and logged the close code.
- Differs: error texts come from Effect: "Transport error (POST …)" instead of "fetch failed", "BadResource: FileSystem.writeFile (…)" instead of Node's error code; a state file that is not JSON says so; a failed `--check` also logs a fatal line.
- Differs: a timer replaced while its event already waits in the queue can still reach the core once, because the stepping fiber may wait on a write in between. The core ignores a timer that no longer applies.
- Differs: log and notification writes wait for a full stderr or stdout pipe to drain, so a session that stops reading stalls the loop until it reads again.
- Differs: `runMain` would exit 130 on a signal; the teardown keeps 0 for a signal or a closed session and 1 for a failure, at once, as before. The log says "stopping: interrupted" for a signal.
- Measured: a planted `Date.now`, `setTimeout`, `fetch`, `WebSocket`, `process`, `Math.random`, `node:fs` and bare `fs` import in the program's files each fail lint. A test runs the whole shell under the real `HttpClient` and `Socket` over a scripted `fetch` and WebSocket: it connects, catches up, delivers once, acks and reconnects when Slack asks. Three more tests catch a mutant each: a reply that asks Slack for a parent the shell already delivered, a timer that is not replaced, and a dead fiber that goes unnoticed. On the real Node layers, `--demo` answers `initialize`, sends its event and exits 0 when stdin closes, also before the session initialized; SIGTERM exits 0; a missing configuration exits 1.

## 2026-11-18: the whole program in the simulated world

BER-2193 completes the structural step described above. `main.ts`, the sampled simulator and the exhaustive pass call `runListener` in `src/program.ts`: the real Slack API client, MCP channel server, saved-state reader and shell. `makeLog` also runs on the simulated stdio. Both independent core-effect interpreters are deleted. The pure core, its rules and production behavior are unchanged (`structure-and-behavior-change-apart`); the shared entry is the smallest composition already needed by three real callers (`steel-thread-first`).

- **Fake boundary:** `src/sim/world.ts` replaces only `FetchHttpClient.Fetch`, `Socket.WebSocketConstructor`, `Stdio` and `FileSystem`, below Effect's real HTTP client and socket. `SimRuntime` supplies the scheduler, clock and seeded choices. HTTP responses, socket events, stdin, stdout and disk operations answer on requesting-process timers. A crash drops those callbacks without finalizers; the next process reads the last atomic rename. The fake retains duplicate and reordered envelopes, reconnect retries, 10% failed connection attempts, flapping catch-up API failures, session-write failures, edits, broadcasts, noise and injection text. History and replies now use three-message pages and opaque cursors, so losing a page reaches R7.
- **Sleep:** a laptop sleep parks process tasks and timers while world posts continue. An overdue timer becomes runnable at wake-up. Timer cancellation uses its unique sequence number, which survives parking; a canceled callback stays canceled. One test covers overdue timers, a canceled callback and a parked ready task.
- **Observation:** the oracle reads the actual JSON-RPC notification content and metadata accepted by stdout, and the actual acknowledgements sent on each fake Slack socket. It no longer renders an ideal delivery beside the program. It checks framing, sender eligibility, duplicates, ordering, thread identity, parent quotes and secrets there; reconnect attempts are timed from the observed close/failure log, and an acknowledgement must use the socket that received its envelope. A delivery-fiber defect at stdout must stop the listener loudly, extending the existing connection-fiber test.
- **R2 identity judgment:** MCP's `edited_at` has second precision. Distinct same-text edits can therefore have the same body; body alone is not an edit identity. The observation checker uses received edit time plus received body. Edits indistinguishable in both fields cannot be distinguished at this boundary. Body line breaks are normalized as the real formatter normalizes them; injected channel tags are checked in the actual output before normalization for comparison.
- **R17 cache judgment:** the unchanged shell caches the first parent it observes in each process; parent edits do not refresh that cache. The independent observer keeps the first per-thread snapshot returned by the fake parent lookup or delivered as a top-level message, and compares the actual parent metadata with that snapshot. It also requires the positive quote for a configured, existing parent, and hides an outsider. Deleted or missing parents can be absent. Enrichment reads remain reliable: the former fake applied API failure to catch-up effects only, and never modeled parent/name/workspace lookup failures. Extending those failures, parent freshness and in-flight deadlines remain outside this structural step. The stale-cache proof substitutes another thread's cached parent, rather than changing that existing freshness policy.
- **End of a run:** terminal recovery clears transient write/API failures and lets the process run. It ends after a live socket, no pending fake I/O and 65 seconds without network/session activity, then checks progress and outstanding acknowledgements. The quiet interval exceeds the 60-second retry cap; periodic state saves and stderr do not reset it, but pending disk writes still prevent closing stdin. A one-hour limit after the final wake bounds a run that never settles. This replaces inspection of private core queues and avoids assuming that all paginated catch-up fits in a fixed 180 seconds.
- **Exhaustive judgment:** each valid prefix is replayed from a fresh program and world because live Effect fibers cannot be cloned. The alphabet and fixed four-second action spacing stay; no core state or effect is interpreted by this driver. A final disconnect is healed before terminal settling, as in the former driver's `settle`. Runtime-dependent prefix validity is reported by the external world, so sequence counts are measured again rather than copied from the old interpreter.
- **Controls and evidence:** one control suppresses observed stdout deliveries; the other presents unfiltered world messages to the same notification observer. The actual program still runs in both. Whole-program replay requires the same seed to reproduce stdout and scheduler traces, and a different seed to change the trace. Catch-rate and timing receipts belong to the exact candidate and are reported with the pull request; no local receipt proves deployment or live Slack behavior.

## 2026-11-18: a fast exhaustive pass

BER-2207. Running the whole program (BER-2193) took depth 7 from about 6 seconds to about 6 minutes on CI. The program's behaviour and the checks are unchanged (`structure-and-behavior-change-apart`); a green pass reaches the same 88,025 sequences. A red pass reports less: a run that fails before its finish reports no next actions, so nothing below a failing prefix runs. It still fails with the same first violation, but with fewer sequences and violations than main counted (a planted R10 bug at depth 4: 224 and 50 against main's 1,088 and 914).

- **The cause was waiting, not Effect.** Between simulated steps the loop waited one real `setImmediate` so promise callbacks could run, about 190 per run. A third of the runs were invalid sequences run in full and thrown away, and every run built a 20,000-entry choice tape (22% of a CI profile).
- **Synchronous drain:** the loop now runs inside one macrotask and drains promise callbacks with V8's microtask checkpoint (`src/sim/host.ts`). It starts with a self-test and refuses a real `process.nextTick`, so the drain cannot silently not drain. The natives-syntax flag stays on: V8 can flush the drain's bytecode and parse it again.
- **Only valid sequences run:** each run reports which next actions its final state allows, from one precondition table, and the pass runs only those. A spec compares the prediction with running every child up to 3 actions, and the depth-5 count is pinned at 3,065, since a wrong "invalid" would drop sequences silently.
- **Split across cores:** the main thread runs sequences shorter than 3 actions and hands the 89 subtrees below to up to 8 worker threads. Violations are sorted into single-thread visiting order; a spec compares the split result with the single-threaded one, and a worker that dies or throws fails the pass by name. A worker that stays alive and never answers would hang the pass until CI's job timeout; the pool has no deadline of its own. No committed check covers the merge and sort of violations, since the parity spec's tree has none; a planted mutation showed the spec fails without the sort.
- **Not taken:** copying state at branch points. Process fork works on macOS and Linux but costs 4-14 ms against a 0.5-2.9 ms replay; a run's fixed cost (about 1 ms of start, finish and checks against 0.15 ms per action) means even a free snapshot saves less than half. Skipping repeated states is the larger lever; Greg parked it, with the other standard optimisations, until the non-obvious options such as fork had been explored. It is BER-2216 step 2. Skipping orderings that end in the same state has not been discussed.
- **CI:** moved to a 4-vCPU Blacksmith runner, faster than GitHub-hosted in the bench; two runs of the same head differed by more than half (45 and 73 s).

## 2026-11-19: what a run costs, and two cuts

BER-2216 steps 2 and 3. The program's behaviour and the checks are unchanged (`structure-and-behavior-change-apart`). Every seed's full result (outcome, failure, steps, coverage, session) hashes the same on main and on this change, and depth 7 gives the same 88,025 sequences, 0 violations and coverage.

- **Repeated states, step 2, not built.** Fable fingerprinted the real state at every prefix boundary of depth 7. With every field, no two prefixes share a state. A view without ids and times, not proven sound, merges 2.1%, 6.4% and 11.9% at lengths 5, 6 and 7, which would save 5.9% of depth 7. The 42% measured on 11-18 compared futures over a short horizon, not states. A view wide enough to merge more would merge a reconnecting prefix with a live one, which differ in catch-up state, and so cut the runs that test catch-up. Parked Effect fibers cannot be fingerprinted either. Look again if the pass goes past depth 8 or the alphabet grows.
- **Where a run's time goes, step 3.** A profile of 30,000 empty runs and 10,000 seven-action runs puts most of the time in the program itself, through Effect's fiber loop, plus the scheduler loop, the microtask drain and garbage collection. An empty run takes 0.25-0.28 ms, and 192 scheduler steps.
- **The end-of-run checks read the world once.** After the last action, the simulator wakes every simulated second until 65 s pass without I/O, about 60 wakes per run. Each wake parsed the saved state and ran the progress check, then threw the result away unless the world was quiet. Now the checks run only on the wake that ends the run, which saves 10-17% on runs with messages.
- **The runtime keeps its trace only when asked.** It built a line for every scheduler step even when nothing read the lines. It now counts the steps and builds lines only when a caller passes a trace, as the replay tests do. A spec shows an untraced run keeps no lines and runs the same schedule. This saves 3-9%.

It also moves the run's end by up to a second, which changes which timers fall due together and so the seeded choices. Every seed would then run differently, and the results could no longer be compared byte for byte.

## 2026-11-19: a reaction says the message arrived

BER-2242, R18. The other side polled with a cron job, every 1 or 10 minutes, to learn whether a message had reached us, and some of those polls timed out. A reaction answers that in seconds. Greg approved the rule and asked for the simple version; the approval was relayed by the session that wrote the rule text. The session does nothing for it: there is no tool and no mark.

- **The core decides, the shell calls Slack.** A delivered message gets an add, and an own-side post in its thread queues a remove for every reacted message before it there. Only one call runs at a time, so a removal never overtakes its addition. The queue is saved before a call starts, so a restart makes it again. Both calls are safe to repeat, because Slack's `already_reacted`, `no_reaction` and `message_not_found` count as done (`safe-to-repeat-compatible-across-versions`). The state file stays version 1. A file written before R18 reads with no reaction state, and older code ignores the new fields.
- **A failing call is given up, loudly.** The shell tries it three times, 1 and 2 seconds apart, then logs the give-up with the message `ts` and Slack's error, never the text (`failure-path-is-part-of-the-contract`). The calls run beside the deliveries, so they hold none up. An app without `reactions:write` gets one such log line per call and delivers as before. The tries do not follow Slack's `Retry-After`, so a burst past the rate limit can give some reactions up, which the rule allows. A full reaction queue (100,000 calls) drops the reaction and logs it; it never stops the listener or holds up a delivery.
- **What counts:** the own side is its people, typed or agent, and its bot. A top-level post answers only its own thread. An edit adds no reaction, and neither does a message that our side had already answered after it when it was delivered, for example both found by one catch-up. A reaction carries no text, so R3's "never posts to Slack" still holds, and `posting` does not gate R18.
- **Anyone else's reaction:** Slack's `reactions.remove` takes off only the caller's own reaction, so the API itself keeps that part of the rule. The fake keeps reactions per user the same way. The simulator checks that every reaction call uses the bot token, the watched channel and the configured emoji.
- **Simulator checks:** on each call, an add only for a message the session was handed, and a remove only after an own-side post later in its thread. At the end of a run, every delivered message carries the reaction exactly while our side has not answered after it. Two cases are excused at the end. The first is a message a call was given up for, meaning the fake failed that call three times in a row, the shell's tries, since the rule allows giving up. The second is a message whose answer was deleted, which the listener may never have seen. While the API is failing, a reaction call fails half the time, and reaction calls take up to 5 seconds, like reads.
- **Mutants, each restored from a copy.** The first review found that the end check excused any message a call had failed for once, so a shell with no retries passed every gate. The check now excuses only a call given up, and these counts are from after that fix:

  | Mutant                                         | 2000 seeds | Exhaustive 5    |

  One call at a time is checked weakly. A removal can overtake its addition only when the answer comes within a call's latency of the delivery, and the sampled world rarely answers that fast.

- **Not taken:**
  - An exhaustive action for an own-side answer. The alphabet has none, so the exhaustive pass checks only additions, and the sampled pass covers removal. Adding a letter would grow every depth. The green pass still reaches the same 88,025 sequences at depth 7.
  - Reading back from Slack which reactions exist after a restart.
- **Open:** RULES.md lists R18 under the step 2 heading, which says posting stays off until `posting: true`. The specifications say R18 applies in step 1, and the code does not gate it. Moving the rule needs the maintainer's approval, so it stays where it was written. Settled the same day: Greg approved moving it to step 1 (next entry).

## 2026-11-19: done, when a message needs no reply

BER-2242, R18 changed. On the first live run, a reply Greg typed in a thread got the reaction itself, and nothing could take it off. His own typed messages are delivered to his session, and an answer from the agent was the only thing that removed a reaction. Greg's direction: the reaction shows the agent received the message, and it comes off once the agent has dealt with it, by answering or by deciding not to. He sends messages to his own agent through the channel, so his typed messages keep getting the reaction. Every delivered message gets it, thread replies included, because the agents mostly talk in threads; one answer clears every earlier reaction in its thread. Greg approved the rule text and the move of R18 to step 1.

- **The tool:** the channel server offers `done`, which takes a message's `ts` and nothing else, so no text of the session's can reach Slack through it. The core ignores a `ts` it never took in and logs it. It keeps the mark, so a `done` that arrives between the write and its delivered event still keeps the reaction off. The session's instructions say to answer in the thread, or call `done` when no reply is needed.

## 2026-11-19: a check mark says the message was handled

BER-2242, R18 changed again. With the reaction taken off, a handled message looked the same as one never delivered, so a sender checking later could not tell "not arrived" from "dealt with". Greg asked for a sign of both outcomes, the agent answering and the agent deciding not to, and for a muted check mark rather than the green one: "it's just not the green checkmark which signals this is done". He approved the rule text.

- **Two marks, one swap:** 👀 (`reaction`) means received and not yet handled; ✔️ (`handledReaction`, default `heavy_check_mark`) means handled, by an answer or by `done`. On handling, the listener queues the add of ✔️ before the removal of 👀, and calls run one at a time, so the message never shows no mark unless the add of ✔️ is given up. A message already answered or marked when it is handed over gets ✔️ at once. Configuration refuses one name for both, since the swap would then take the only mark off.
- **Kept apart from what was there:** each queued call names its mark. A state file written by the previous version holds calls without one; they are read as 👀 calls, which is all that version queued. The handled messages are kept in their own map, so an older file reads as having none. Messages handled before the upgrade, including any whose 👀 removal is still queued then, stay without a mark: the listener has already let them go, so a later answer or `done` changes nothing. Going back is not clean any more: the previous version sends every queued call as 👀, so a ✔️ call queued at that moment becomes a 👀 call, and a message handled at delivery could keep 👀 beside its ✔️. The earlier entry's "older code ignores the new fields" holds only for the fields, not for the queued calls.
- **Not chosen:** keeping 👀 and adding ✔️ after every answer would show a final state on every message, but fills threads with marks when the reply already says it. Removing the swap on a given-up add of ✔️ was not built: a given-up call is the rule's one exception already, and the message then shows no mark, as before this change.
- **Simulator:** each reaction call is checked as it reaches the fake. 👀 goes only on a delivered message; ✔️ only once an own answer exists or `done` was sent, and it never comes off; 👀 comes off only while ✔️ is already on, unless the message is gone or a call for it was given up. At the end, each delivered message carries exactly one mark: ✔️ when handled, 👀 otherwise.

## 2026-11-22: retries on Effect's schedules (BER-2354)

Step 4b of the plan, a structure change. `effect-does-the-waiting` named two retry loops beside Effect's: the core computed the reconnect backoff and sent it out as a timer command, which the shell turned back into a sleeping fiber, and the shell retried a reaction call in a recursive loop around `Effect.sleep`. Both now run on `Schedule`, with the same delays and caps. No rule text changed.

- **The attempt count and the schedule live in the shell.** The core keeps its decisions about the connection: when the listener is live, when it reconnects, and dropping a stale socket's events by generation. For a failed try it now says only which run of tries the wait belongs to (`back_off`, on the `connection` or the `delivery` run) and when a run is over (`reset_backoff`). The shell steps one copy of `backoffSchedule` per run with `Schedule.toStep`, in the order the core decided the waits, and starts a fresh copy on a reset. The count is the schedule's own: the core's `attempt`, `sinkAttempt` and `backoffMs` are gone.
- **Not chosen: the count in the core, the schedule in the shell.** The core would have sent the attempt number, and the shell would have asked the schedule for that step's delay. The reset would have stayed a plain state change, but the shell would replay the schedule from its start for every wait, or know its shape to skip ahead, and the core would still hold the schedule's state. With the count in the shell, the end of a run becomes a command; it is idempotent and costs one effect each time the listener goes live and each time a delivery is written.
- **More than the plan row named.** The core computed two more waits with `backoffMs`: a failed catch-up's, on the reconnect's own count, so a failed catch-up lengthened the next reconnect wait and both started over only when live; and a failed delivery's, on `sinkAttempt`, which started over once a delivery was written. Taking the computation out of the core meant moving both. Catch-up retries share the connection's run, as they shared its count; deliveries have a run of their own.
- **Same waits.** 1 s, doubling, capped at `maxBackoffMs` (60 s): `Schedule.exponential` with `modifyDelay`. The wait still counts from the step that decided it, so a timer is due at the same millisecond as before. The old code capped the exponent at 16 against overflow; the schedule's doubling reaches Infinity after 1,024 tries, about 17 hours of outage, and a test shows the cap still holds there. `maxBackoffMs` stays in `CoreConfig` with the other limits, although only the shell reads it now. The reaction call is `Effect.retry` on `Schedule.exponential(1 s)` with at most two retries: three tries at 0, 1 and 3 s. ## 2026-11-22: the action contract (BER-2357)

Slice A of the action contract: one definition per action, from which a REST API with its OpenAPI document, an MCP toolkit and AtomHttpApi query and mutation atoms are generated, with a property that every surface gives the same answers. It lives in `src/action/` as new files beside the listener and changes none of the listener's code; `.oxlintrc.json` adds the non-spec files to the `world-through-services` bans (a planted `Date.now()` in `receipts.ts` fails the lint). The example is `getReceipt(eventId)`, a query, and `acknowledge(eventId)`, a mutation that is idempotent per caller and event, over an in-memory store, with the errors `UnknownEvent` and `NotAllowed`. Effect 4.1.4, Bun 1.4.5, no new dependency.

- **The shape.** `defineAction({ name, description, kind, input, success, errors, permission, handler })`. `input` is an object of named Schema fields, never a bare value: MCP requires an object root and a query's fields become its query string. `success` and each error are Schemas that need no services, so every surface runs them as they are; each error is a `Schema.TaggedError` with a `message` field and an `httpApiStatus` annotation. `permission` names what a caller needs (`"receipts.read"`, `"receipts.acknowledge"`); the definition holds no table of who has it. `handler(input, principal)` is an Effect whose failure type is exactly the declared errors and whose own services (`R`) are given once with `provideAction`, so the projections only ever see actions that need nothing. `defineAction` refuses a bad name, an empty description, an empty permission, a tag declared twice and a redeclared refusal at definition time. It returns the definition with `inputSchema` (the struct) and `failure` (the errors plus `Unauthenticated` and `NotAllowed`), which every projection declares as is.
- **One way into a handler.** Every surface calls `invokeDecoded(action, principal, input, services)`, which checks with `Schema.is` that the surface decoded the input and dies otherwise (a surface that skipped decoding is a bug, not a refusal, and there is no cast between the decode and the read: `decode-at-the-boundary`), then `invoke`: no principal fails with `Unauthenticated`, a principal the `Policy` does not grant the action's permission fails with `NotAllowed`, otherwise the handler runs.
- **The caller is a principal.** Set by the owner on 2026-11-22, so the contract fits the platform (porta runs the agents in sandboxes; iron-proxy injects secrets on the wire per principal). A principal is an opaque string id; the contract never looks inside it and keeps no user model of its own. Examples use iron-control's naming, `slack-user-<team>-<user>` for a person and `slack-channel-<channel>` for a channel, with lowercase placeholder ids (`slack-user-t0000-u0001`, `slack-channel-c0001`), since iron-control slugifies principal ids to lowercase. `Principals.authenticate(bearer)` maps the bearer a client sends to the hub to a principal or to none.
- **The permission check is a service.** `Policy.allows(principal, permission)` answers, provided by a Layer; it returns an Effect so an implementation may ask another service. The slice's Layer is an in-memory grant table (`policy.ts`); iron-control's roles and grants can provide the same service later without any action changing, and a test runs the same actions under two grant tables and gets the refusal under one and the receipt under the other on every surface. A named permission rather than a predicate in the definition keeps who-may-do-what out of the action, where the platform can own it.
- **No secret in the contract.** No type in it carries a credential: a handler receives the decoded input and the principal, and an outbound call it makes later (Slack) goes through iron-proxy, which adds the credential on the wire. The only credential is the transport's own bearer to the hub, which stops at the surface that resolves it. Beyond the types, the handler runs on the context its surface was built with instead of the request's (`Effect.updateContext` in `invokeDecoded`): before that change a handler's fiber context still held the request with its `Authorization` header (and, while MCP's tests still sent the bearer in `_meta`, MCP's request context with it), out of reach of its type but not of a cast. Each surface reports the keys of the context it is built with (`surfaceServices`, through the `SurfaceServices` reference, which does nothing unless a test listens), and a test calls an action on every surface and checks that its handler sees the principal and exactly those keys, so any service the request adds fails it, whatever its name or content. Planting the old `Effect.provideContext` back fails it, and so does dropping the swap: the handler then also sees 5 keys its surface was not built with on REST and atoms (`HttpServerRequest`, `CurrentRequestState`, `ParsedSearchParams`, `RouteContext`, `CurrentPrincipal`), 25 on MCP and none on the direct surface. An earlier version of the test scanned each service's JSON for the bearer; the review found that it reported no leak on any surface even with the swap removed, so it proved nothing and is gone. The cost: a handler no longer inherits the request's span as its parent.
- **How the caller travels.** Each surface turns its own bearer into a principal through the one `Principals` service, so a bearer means the same principal everywhere, and none of them refuses by itself. REST: a bearer token, declared with `HttpApiSecurity.bearer` on an `HttpApiMiddleware` that provides `CurrentPrincipal`; the OpenAPI document shows the scheme. MCP: the `Authorization` header of the Streamable HTTP transport, read by an `McpServer.middleware`, on the stateless 2026-07-28 protocol so that every call carries its own. The bearer is never in the JSON-RPC payload, where a log of the messages would keep it: an earlier version also read it from the request's `_meta` because `McpTest` cannot set headers, and the review rejected that. The world now serves the REST API and the MCP endpoint (`McpServer.layerHttp`) from one router behind the same in-process fetch, and its MCP calls are plain `tools/call` POSTs with the header set, as any MCP client sends them; Effect's `McpClient` is experimental and the lint refuses it. A test posts a call with the bearer only in `_meta` and gets `Unauthenticated`. How a stdio session authenticates is open: stdio has no header, so today it has no principal and every call is refused; an adapter runs per session, so the principal could be fixed when it connects. Not built. Atoms: the HTTP client's bearer, one atom client per bearer whose client side of the same middleware sets the bearer token, as a signed-in UI does.
- **Input is checked before the caller.** On every surface a call with an invalid input answers invalid whether or not it has a principal: the surface decodes first and `invoke` refuses after. Kept as a choice: the atom client refuses an invalid input before it sends anything, so only decode-first gives the same answer on every surface, and the input schemas are public in the OpenAPI document and the tool list, so the order discloses nothing.
- **The error-mapping rule.** One definition per error, three forms. REST answers with the error's declared status and its JSON encoding as the body; the OpenAPI document lists every declared error under its status with its `_tag`. MCP answers with a tool result marked `isError` whose one text content is the same JSON encoding (`failureMode: "return"`). Atoms fail with the decoded error itself, a typed failure in the `AsyncResult`. An invalid input is not an action error: REST answers an empty 400, MCP its "Invalid parameters for tool" text, and an atom client refuses it before sending (a `SchemaError`, no request). An unexpected failure answers an empty 500, MCP's fixed internal-error text and an atom defect; no surface carries its message, and McpServer logs it on the server (`surfaces.spec.ts` plants a secret in a dying handler and checks both).
- **One difference in what the documents say.** The OpenAPI document gives each input object `additionalProperties: false`; MCP's tool list and `Schema.toJsonSchemaDocument` give `true`. Every decoder ignores an extra field (Effect's default `onExcessProperty: "ignore"`), and the agreement property sends one, so the surfaces behave alike; only the documents differ. The drift check compares everything else.
- **What proves agreement.** `surfaces.spec.ts`: fast-check sequences of up to 16 calls of (action, input, bearer, surface), with known, unknown and malformed ids, wrong types, a missing and an extra field, and six bearers (two Slack users who may read and acknowledge, a channel that may only read, a user with no grant, an unknown bearer, none). Each sequence runs five times on a fresh store: through the surface each call names, through each surface alone, and directly through `invoke` as the oracle; every call must give the same observation and every run must leave the same store. A REST answer must also carry the status its error declares. `contract.spec.ts` is the drift check: the OpenAPI document's paths, operation ids, inputs, outputs, error responses and their components, and MCP's tool names, input and output schemas and read-only hints, all against the definitions, and a client that reads only the document (path, method, where the input goes, the security scheme) calls `getReceipt` and gets a body with exactly the documented fields.
- **The scheduler: yes, with one change of budget.** All three in-process clients run under `SimRuntime` with no real timer and no `process.nextTick`: the HTTP handler for REST and MCP runs on the builder's context (`HttpRouter.toHttpEffect` and `HttpEffect.toWebHandlerWith`, not `toWebHandler`, which builds its layer with `Effect.runPromise` on the default scheduler), the MCP clients are built in the same scope, and the atom registry's tasks go to the builder's dispatcher through `scheduleTask` (without it, `AtomRegistry` schedules with Promise microtasks). Each HTTP answer, REST, MCP or atom, reaches its client after a seeded delay on the simulated clock. The seed replays: the same seed gives the same trace and the same answers, two seeds give different traces, and the tripwire stays empty on every run. What the seed does not pick: Effect resumes a fiber from a callback by calling it directly, so continuations after a promise run in the host's microtask drain in JavaScriptCore's order; in a smoke run with the earlier `McpTest` harness, REST and atom calls showed no scheduler entries of their own and MCP calls 33.
- **Liveness failures, which the seeded budget reaches.** The simulator gives each turn a seeded budget of 2048 down to 1 operations. With it, on the earlier `McpTest` harness, about one seed in 200 of a sequence ended stuck. Cause one, found by instrumenting the stuck fiber: a fiber forked but not yet started is interrupted; the interrupt's own evaluation yields at its first operation; the fiber's pending start task then cancels that yield and runs the body, and the interrupt is lost. A scope closing over such a fiber (here an `McpTest` client, as the harness then used, built and closed with no call) waits forever. Effect's default budget of 2048 never yields at a first operation; a budget of 1 does. `effect-liveness.spec.ts` reproduces it with Effect alone and a hand-drained scheduler: the interrupted fiber ends under a budget of 2048 and is still running under 1. Cause two is not found, and not attributed: a bare `McpTest` server with a one-tool toolkit of its own and none of the contract's code leaves a `ping` unanswered for seeds 216, 2695, 2732 and 2870 of 0 to 2999 (three clients per run), and for none when the budget is fixed at 2048. Cause three is not attributed either: the same bare server over Streamable HTTP (`McpServer.layerHttp` behind the web handler on the builder's context, twelve `tools/call` POSTs per run, each answer after a seeded 0 to 20 ms) answers an empty 500, from McpServer's own "MCP request ended without writing its response", for seeds 1333, 1616, 2077 and 2219 of 0 to 2999, and only 200s under the fixed budget. So neither is the contract's fault; nothing shows whether Effect or the simulator causes them. Seed 216 (in memory) and seed 1333 (over HTTP) are pinned on the bare server. The atom harness mounts each atom for its call, as a component does; an earlier stall put down to an unmounted atom was cause one again. (Later: all three causes are Effect bugs, root-caused and patched in "Effect patched for the seeded budget (BER-2365)" below.)
- **The fixed budget stays, measured on the current world.** Re-measured on the world as it now is (one router serving REST and MCP, MCP calls as plain POSTs, no `McpTest`): 500 fast-check sequences (seed 23) times 10 simulator seeds, 5000 runs. With the seeded budget: 0 stuck, 0 disagreeing, 3 failed (seeds 1719, 2149 and 2610, each an MCP call answered with that same empty 500, cause three). With the fixed budget: 0 stuck, 0 disagreeing, 0 failed. The reviewer's 1000 runs with the seeded budget gave 0 stuck and 0 disagreeing. No run sticks any more, but about 3 in 5000 fail on cause three, so `runSimulated` keeps the simulator's dispatcher, clock and seeded task order and every HTTP delay, and replaces only the per-turn budget with Effect's own 2048 (`withFixedBudget`, in this slice's code, no change to `src/sim`). The cost: the seed no longer picks where a fiber is preempted. `SimRuntime` still draws a budget every turn and the fixed scheduler ignores it, so the other choices a seed makes stay as they were, but no run explores a preemption inside a turn. A narrower floor was tried. My own measurement: with no budget below 2, the bare `McpTest` server still stalls on seeds 216, 2105, 2732 and 2870 of 0 to 2999. The reviewer measured the floor of 2 on the contract's registrations, over seeds 0 to 1499: seed 216 still stalled and seed 1448 recovered. So the budget is fixed outright. The pinned tests fail when a change fixes a cause, which is when `withFixedBudget` can be reconsidered. The listener's own simulator keeps the seeded budget and passes; it would hit cause one only by interrupting a fiber before its first run. (Later: `withFixedBudget` is gone and the seed picks preemption points again; see "Effect patched for the seeded budget (BER-2365)" below.)

## 2026-11-22: RPC as a fourth surface (BER-2363)

The owner: "Note that if rpc is simple then let's also have it". It is: `src/action/rpc.ts` projects the same definitions to Effect RPC (`effect/rpc`, unstable in 4.1.4 like `http-api`) in 134 lines, 98 of them code, with no change to the REST, MCP or atom projections, no patch to Effect and no new dependency. The harness gains `rpc` as a surface (101 lines in `harness.ts`, mostly the client), so the agreement property now compares five runs plus the mixed one.

- **The projection.** Each action is one `Rpc.make(action.name, { payload: action.inputSchema, success: action.success, error: Schema.Union(action.failure), defect })`, and the actions form one `RpcGroup` with the `Authentication` middleware on every procedure. `group.toLayer` gives each one a handler that reads `CurrentPrincipal` and calls `invokeDecoded(action, principal, payload, services)`, where `services` is the context the handler layer was built in, reported through `surfaceServices("rpc")`: the refusals stay in `invoke` and the handler runs on the surface's build-time context, as on the other surfaces. `RpcServer.layerHttp({ protocol: "http" })` with `RpcSerialization.layerJson` puts one POST route, `/rpc`, on the router that serves REST and MCP; request and answer are each one JSON body, so it runs behind the world's in-process fetch as the others do, plain and under `SimRuntime` with the same `withFixedBudget` (removed in BER-2365 below).
- **How the caller travels.** As a bearer in the `Authorization` header of the HTTP request that carries the RPC messages. The `Authentication` middleware (`RpcMiddleware.Service`, providing `CurrentPrincipal`) reads that header from the request's `HttpServerRequest` and resolves it through `Principals`, and never refuses. It does not read the `headers` RpcServer passes to a middleware: those are the HTTP headers with the RPC message's own `headers` appended (`requestHeaders.concat(message.headers)`), and the message travels in the JSON body, so reading them would take a bearer from the payload, which the MCP review rejected. A test posts a call with `authorization` only in the message's headers and gets `Unauthenticated`, and one with an unknown bearer in the HTTP header and a known one in the message also gets `Unauthenticated`. A transport with no HTTP request (a socket, a worker) has no header, so no principal; nothing here serves one. The client side needs no middleware: the harness's `RpcClient` sets the bearer on its `HttpClient`, as an outside client would.
- **The error mapping.** The RPC form of the rule: an action's declared error, and the two refusals, reach an `RpcClient` as the decoded error itself, the call's typed failure (a test checks `instanceof UnknownEvent`, `Unauthenticated` and `NotAllowed`). A defect reaches it as a die with a fixed `Error("internal error")`: the Rpc's defect schema encodes any defect as `null`. The default, `Schema.Defect()`, would send the defect's name and message, and by default RpcServer also treats a handler defect as fatal and sends it as a client-wide `Defect` message that ends every pending call of that client, encoded with `Schema.Defect()` again; `disableFatalDefects: true` keeps it the call's own failure. A test plants a secret in a dying handler and checks that neither the client's cause nor the raw answer carries it (the answer is `{"_tag":"Die","defect":null}`) and that the server reports it: RpcServer passes a failed call to the `ErrorReporter`s, not to the logger as McpServer does, so an operator needs a reporter to see it. An invalid input never leaves the `RpcClient`: it builds the payload with the schema's `make`, which throws an `Error` whose cause is the schema issue, so the harness counts a throw with an issue as its cause before any request as invalid, as it counts the atom client's `SchemaError`. An invalid input posted past the client is decoded by the server, which answers that call with a die, so it comes back as the same `null` defect, where REST answers an empty 400. MCP's form, a tool error, and REST's, a status, are unchanged.
- **What was simple.** `Rpc.make` takes the definition's schemas as they are; the group's handlers are a record by name, as `handleAll` is on REST; the server is one layer on the existing router; the handler-context test needed one entry (`rpc: "rpc"`), and without the swap the RPC handler sees 7 keys its surface was not built with (`HttpServerRequest`, `CurrentPrincipal`, `RouteContext` among them). `OpenRpc.fromRpcGroup` produces a document in one call; the drift check compares each method's parameters and result with the definitions and with the OpenAPI input.

The OpenRPC document lists no typed error: OpenRPC's `errors` are JSON-RPC codes with a literal message, and Effect derives them only from such schemas, which the contract's errors are not.

- **What streaming RPC would add later.** Not built. ## 2026-11-22: the task hub, B1: the store and its actions (BER-2368)

The owner approved slice B on 2026-11-22: "B can go". Time is lost because nothing records what each task waits on, from whom and since when, so nobody notices a question or a red CI. The task hub is that record, shared by people and agents. B1 is its first step: a store, twelve actions on the action contract (eleven at first; the inbox's `taskWaiting` came with the addendum below) (BER-2357, RPC BER-2363) and the rules T1 to T7, with a simulator of their own. It lives in `src/hub/` beside the listener and changes none of the listener's code; `agreement.ts` gains a runner that takes any fixture. The listener's 2000 seeds give the same full results as main (`a78246b8…63f2b`, by one script on both), and depth 7 the same sequences and coverage. One new dependency, `@effect/sql-sqlite-bun` 4.1.4, as the store spike recommended.

- **Where the domain comes from.** The six states are A2A's task states (`submitted`, `working`, `input-required`, `completed`, `failed`, `canceled`; A2A's `rejected`, `auth-required` and `unknown` are left out). From Vercel's Board: a worker claims a task under a lease, a task ends with a result, and every change names its actor. From eggp: the store has one writer. The request key is the usual idempotency key.
- **One transition table.** `transitions` in `src/hub/task.ts` has one row per command: the states it may start from, who may make it, what the lease must be, the state it leads to and the change it records. `decide(task, command, actor, now)` checks a command against its row, in the order state, lease, actor, option, and returns the change or a typed refusal. `evolve(task, event)` applies a change and takes the next state from the same row. Nothing else moves a task; even a claim picks its task by asking `decide` (`pickReady`), so the lease check has one home.

  | Command      | From                               | Who                     | Lease                | To             | Records          |
  | ------------ | ---------------------------------- | ----------------------- | -------------------- | -------------- | ---------------- |
  | claim        | submitted, working                 | anyone granted it       | none live            | working        | `claimed`        |
  | renew        | working                            | the holder              | held by caller, live | same           | `renewed`        |
  | requestInput | working                            | the holder              | held by caller, live | input-required | `inputRequested` |
  | answer       | input-required                     | the principal waited on | any                  | working        | `answered`       |
  | amend        | submitted, working, input-required | the creator             | any                  | same           | `amended`        |
  | cancel       | submitted, working, input-required | the creator             | any                  | canceled       | `canceled`       |
  | complete     | working                            | the holder              | held by caller, live | completed      | `completed`      |
  | fail         | working                            | the holder              | held by caller, live | failed         | `failed`         |

  Create is no row: it makes a `submitted` task with a `created` event.

- **The actions.** Action names must be camelCase (`defineAction`'s name pattern), so `task.create` is `taskCreate` and so on; each has its own permission, `task.create`, `task.claim`, `task.renew`, `task.requestInput`, `task.answer`, `task.amend`, `task.cancel`, `task.complete`, `task.fail`, `task.get` and `task.events`. Every mutation answers the task after its event and the event's cursor; a claim answers `Claimed` with them or `NoneReady`, a typed result, not an error. The errors, each a tagged error with its status: `TaskNotFound` 404, `WrongState` 409, `LeaseNotHeld` 409 (not the holder, or the lease lapsed), `NotWaitingOnYou` 403, `NotCreator` 403, `NotAnOption` 422 and `RequestKeyReused` 422. `NotAnOption` is one more than the brief listed: T5 needs an answer outside the options refused, and none of the others says so. Each action declares exactly the errors its row can give (create and claim only `RequestKeyReused`; `taskGet` only `TaskNotFound`; `taskEvents` none); the store answers with any refusal, and the action narrows it, dying on an undeclared one. Permission refusals stay the Policy's, in `invoke`.
- **The lease runs, except while the task waits.** A lease is live until its expiry instant. A working task whose lease lapsed is ready again, and its old holder's renew, requestInput, complete and fail are refused with `LeaseNotHeld`. While a task is `input-required` the lease is suspended: `requestInput` keeps what was left (`leaseRemainingMs`) and `answer` starts it again with that much. The holder cannot move the task while someone else holds the next move, so a lease that ran on would punish the holder for a slow answer and hand the task to another claimant mid-question. The claimant keeps the claim while waiting and sees the answer as an `answered` event.
- **Request keys.** A key belongs to its principal: two principals' equal keys never meet, so one cannot read another's answer. The store records every answer under its key, refusals too, in the same transaction, so a repeat returns the first answer even when the task has moved since; a refusal records its answer with no event. The request is compared as canonical JSON of the store request (action and input, keys sorted); the same key with another request is `RequestKeyReused` and records nothing. Keys do not expire yet.
- **Events and the tasks table: both, in one transaction.** The events are the record; `hub_tasks` is their projection, updated in the same transaction by `evolve`, so a read needs no fold. The cursor is the next integer after the largest, taken inside the write transaction, so cursors follow commit order with no gap; a task's id is `T` and the cursor of its `created` event. The checker replays the events and compares the projection.
- **The store.** effect/sql over `@effect/sql-sqlite-bun`, WAL, `BEGIN IMMEDIATE` per mutation; the time is read once per mutation from Effect's Clock, inside the write transaction (see the fix round below). The DML is portable SQL (`IN`, `COALESCE`, `LIMIT`, no `INSERT OR`); a Postgres Layer would bring its own table definitions. `holdWriterLock(file)` is the single-writer lock from the spike, `BEGIN EXCLUSIVE` on a file of its own, held until its scope closes; a test shows a second holder refused until the first lets go. No program takes it yet (B2). The hub adds no transport: it is served only through the contract's surfaces, and its principals come from `Principals` and the `Policy` as the receipts' do.
- **The agreement property** runs the hub's actions through REST, MCP, RPC, the atoms and `invoke` on a fresh in-memory store per run, with sequences of up to 24 calls over existing and missing tasks, repeated and reused keys, all eight bearers and invalid inputs, plain (120 runs) and under the seeded scheduler (100 runs). Each call is made at a time the sequence sets, through a clock whose time the test sets and whose sleep is the one beneath (`settableClock`), so leases lapse the same way on every surface. The handler-context test calls every hub action on every surface and checks its handler runs on exactly the services its surface was built with.
- **The simulator** (`src/hub/sim`, `bun run sim:hub`, 500 seeds of 80 calls in CI, about 30 s). One process holds the store over a SQLite file and the surfaces over it; the driver, the checker's model and the disk live in the world. Calls come from four principals with every grant and, rarely, the channel, a user with none and an unknown bearer, each through a random surface, with waits of up to 4 s on the simulated clock so leases lapse. 8 % of calls repeat the last mutation's key, most with the same input, the rest with another. Crashes, at most four a run, come from a world timer at a seeded time and from a seeded crash before any statement the store runs, inside a write transaction or outside it: the simulator wraps the process's SQL client, so the store has no hook of its own. A crash copies the database and its write-ahead log as they are on disk and starts a new process on the copy; the call in flight is sent again with the same key. The crash before a statement is a world timer due at once, while the statement's fiber waits forever and holds the connection: a statement can run inside the host's microtask drain, and crashing there let the rest of the drain schedule timers for the dead process. After every step the checker replays the store's events against T1 to T5 on its own, compares the answer with a reference model, a second implementation of the rules written without the table, and compares the store with the model; after a restart the store must equal the model before or after the call in flight (T7). A seed replays to the same scheduler count and coverage.

- **Fix round, the same day, from the TLA+ spike.** A TLA+ model of the hub's protocol (`.notes/4-architecture/slack-mcp-spec-review-2026-11-22/spikes/tla-tasks`, TLC 2026.11.02, written from the brief without reading the code) passed every safety rule and caught each of its 11 planted bugs, and found two things the code gets wrong:
  - **The clock is read inside the write transaction.** `execute` read `Clock.currentTimeMillis` before `sql.withTransaction`, and the SQLite client serialises transactions, so a call queued behind others decided with the time it arrived. A stale holder's renew, requestInput, complete or fail could then be accepted up to the queueing delay after its lease lapsed (when nobody had reclaimed it; the claimant check still keeps one holder), and an event's `at` could go back in cursor order. The model assumes lock, then clock, and its T2 and T4 hold that way. The read now sits inside the transaction, and the write asserts that a new event's `at` is never before the last event's: a clock gone back refuses the write as a defect, and the transaction rolls back. A spec shows it, and a plant that drops the assertion fails it. The simulator sends one call at a time, so it cannot race two calls: a plant that moves the read back outside passes the simulator and every spec, as expected. B2 proves the order with two calls in flight.
  - **Claims go least recently claimed first.** TLC's liveness run (`design-oldestFirstStarves`, 849,008 states, 2 min 40 s) found a lasso with oldest-first claims: one fair worker, two tasks; it claims t1 and t2, both lapse, and from then on it claims t1, lets it lapse and claims t1 again, while t2 stays lapsed forever. A poison task that keeps lapsing blocks every younger lapsed task the same way. Claims now take the ready task claimed least recently: never claimed first, then by the time of the last claim, ties in creation order. Each task records `claimedAt`, set by its `claimed` event. With that order the spike's `live` run (`LapsedIsReclaimed`, 1,640,216 states) passes. A spec replays the lasso: one worker, two tasks, t1 claimed and left to lapse, and the next claims take T2, T1, T2 in turn. Planting oldest first back fails that spec and 160 of 200 simulator seeds, whose model orders claims the same way. Fewer claims now land on a lapsed task, since a never-claimed one goes first: at 200 seeds on that commit `lapsedReclaimed` fell from 467 to 186, and refused stale-holder calls rose from 350 to 547.
  - **A poller needs a new request key per poll.** The store records "none ready" under its key like any answer, so a poller that reuses a key gets that stored "none ready" forever, even after a task becomes ready. Each poll takes a fresh key; a retry of the same poll keeps it. B2's sessions poll this way.

    - **The lease boundary is pinned.** A lease is live while now is before its expiry instant. A spec claims at 10 for 1000 ms: at 1009 another claim finds none ready; at 1010 the old holder's renew is refused with `LeaseNotHeld` and a new claim succeeds. A claim scans every submitted and working task and orders and filters them in memory. A question has no deadline: if the principal it waits on disappears, only the creator's cancel moves the task; its age in the inbox is the signal for now (the spike's `InputRequiredEnds` fails, as expected). A deadline on `taskRequestInput`, or a fallback to the creator, would close it. The inbox filters waiting tasks in memory too; the channel principal has no `task.waiting`, on least privilege, since nothing needs it before slice C. Request keys and events are kept forever. `taskEvents` reads the whole feed, with no filter by task. A query atom does not see a write made through another surface (as for the receipts). The tables are SQLite's; the Postgres DDL and `pg_advisory_lock` are not written.

## 2026-11-22: the task hub, B1c: the round trip between the TLA+ model and the code (BER-2368)

The B1 spike's TLA+ model (`Tasks.tla`) was written from the brief without reading the code, and the code was checked by its own simulator against its own reference model. Neither said whether the two describe the same protocol. B1c checks that both ways: paths TLC finds in the model are replayed through the hub's real actions (model to code), and traces the hub records are checked by TLC against the model (code to model).

- **The spec moves into the repository**, `spec/tasks/` with its configurations, `tlc.sh` (a capped TLC run) and a README on running TLC locally. Authority stays RULES.md, then `Tasks.tla`, then the transition table. Three changes to the spike's spec:
  - **Claims go least recently claimed first.** The spike's `ReclaimLast` became `OldestFirst`, FALSE everywhere except `design-oldestFirstStarves`, which keeps the lasso as a design record. `b1.cfg` still passes: 1,068,408 states, depth 23, 55 s. Each of the ten `b1-bug-*` configurations is still caught by its rule.
  - **A disagreement on refusal order, settled for the code.** The spike checked a creator's amend or cancel for its actor before its state; the code checks the state first (`decide`: state, lease, actor, option), so a stranger's cancel on a final task is `WrongState` in the code and `notCreator` in the spike. This is the order two refusals are reported in, not a rule: RULES.md says both refuse, and both still do. The spec now checks the state first (`CreatorStep`). No rule changed.
  - **A commit is split from its reply.** The spike's `Commit` also delivered the answer, so it could not say "committed, answer lost", which is the simulator's most useful crash. `Commit` now leaves the answer in `out`, and `Reply` delivers it or `LoseReply` drops it; nothing else moves while `out` is set. T1–T7 are unchanged and still hold.
- **The abstraction, α** (`src/hub/sim/alpha.ts`), maps a store snapshot and the time to what the model keeps: per task its state, creator, holder, the lease left in whole ticks (1 tick = 1,000 ms; while input-required, what is kept), and whom it waits on; the event log as (task, kind, actor, key, argument, the state it led to); and per principal and key the stored input and the answer's code and task. The snapshot gained the stored requests (`memo`) for this; nothing else in the store changed. α drops the rest, and each dropped field cannot change T1–T7:
  - **Texts** (title, labels, question, instructions, result, reason) never reach `decide`, which reads only the state, the lease, the actor and the option; the replay sends fixed texts.
  - **Options** are always `o1`, `o2`, and `o3` is the one not offered; T5 only asks whether an option is offered.
  - **Absolute times.** Every replayed call lands on a tick boundary with no delay before its answer, so every lease is a whole number of ticks and `left` is exact; the lease boundary inside a tick is pinned by its own spec (B1). Event times and the inbox's ages are not in α; the store's assertion that events never go back in time stays the check for them.
  - **Cursors and task ids.** T4 makes cursors consecutive in commit order, so the log's positions say what they say; with one task its id is `T1`.
    A replayed call's answer code is compared as well as α, so a refusal that leaves the store as it was still has to be the model's refusal.
- **Model to code.** `regenerate.sh` (local, about 10 minutes) has TLC dump `b1-export`'s state graph (`b1.cfg` with `VIEW ExportView`: 144,148 states, 5,093,309 edges, a 1.3 GB dot file) and runs the ten bug configurations; `src/hub/sim/tla/export.ts` cuts the fixture `spec/tasks/replay.jsonl`:
  - one shortest path to every class of at-rest call, where a class is the action, the answer, the state, the caller's relation to the creator, holder and waited-on principal, the lease left, whether the key is stored and whether the task bound is reached; each call that commits gets three paths, answered, its answer lost after the commit, and crashed before the commit; and one path per class of tick;
  - every planted bug's counterexample, with `failAt`, the first code step that covers the bug's first move outside the correct graph.
    The model's create refusal at its task bound (`full`) is an artefact of the bound (the code has no task limit), so those states and classes are left out. The first fixture was 3.76 MB; writing α as one short string per task, event and key (`compactOf`) brought it to 1,929,167 bytes (1,367 lines) with the same selection, so the selection was not reduced. One TLC worker makes the file the same on every run (two runs of `regenerate.sh`, 9 min 45 s and 9 min 38 s, compared with `cmp`: equal).
  - **The replay** (`bun run sim:hub:replay`, in CI and AGENTS.md) runs each path on the hub simulator in a fixed mode: a seeded random surface per call (REST, MCP, RPC, atoms, `invoke`), answers at once, a model call is `execute`, a crash is the simulator's crash before the transaction's first statement, a lost answer is a crash after the call returned, a tick is `Effect.sleep` of 1,000 ms on the simulator's clock. After every step it compares α and the answer's code, and the simulator's own checker (the event replay, the reference model, the restart check) runs as always. Result on this branch: 1,367 paths (1,357 of the correct model, 10 planted bugs), 6,682 steps, 0 failures, 12.4 s locally (the brief estimated 25 s). The bugs fail at: `answerAnyOption`, `answerAnyPrincipal`, `cancelKeepsWait` and `reopenCompleted` step 3, `renewAfterLapse` step 4, `claimSkipsLease` step 2, `ignoreMemo` step 1, `eventOutsideTx` and `memoOutsideTx` step 0 (a create that crashes before its commit leaves no event and no stored key in the code, and one of them in the buggy model). Every correct path passes; every planted bug's path fails at its `failAt` step, except `dirtyRead`, which needs a read inside another caller's open transaction and cannot be replayed one call at a time.
  - **A counterexample against its mutant.** With renew accepted after the lease lapsed (`holds = (live || rule === transitions.renew) && ...`, copied aside, restored with `cp`, checked with `cmp`), `renewAfterLapse`'s counterexample replays with α matching the buggy model up to its step 4, where the checker stops it: "T2: renewed on T1 by slack-user-t0000-u0002, not the live holder"; two correct paths (a stale holder's renew refused with `notHolder`) fail the same way. With claim's lease check skipped, `claimSkipsLease`'s counterexample stops at its step 2: "T2: slack-user-t0000-u0001 claimed T1 while slack-user-t0000-u0002 held a live lease"; 16 paths fail in all.
- **Code to model.** The simulator's bounded mode (`BoundedMode` in `src/hub/sim/conform.ts`) stays inside the model's bounds: two principals, one task, two keys each, at most four events, waits of one or two ticks, two crashes per hundred statements while a call is in flight, a crashed call sent again. It records α after every call, lost answer and wait; a crash that left the store as it was is a stutter and records nothing. `src/hub/sim/tla/validate.ts` writes each trace into `TraceTasks.tla` (trace validation in the style of Cirstea, Kuppe, Loillier and Merz, 2024: each line is one group of the spec's steps, which must end at rest with α equal to the line's, and the call's answer stored under its key) and runs TLC; a trace is accepted when TLC consumes all of it. 100 seeds of 12 calls: 1,643 lines (1,200 calls, 21 lost answers, 322 waits), all accepted, 36 s. With renew accepted after lapse, seed 88 is rejected: TLC reaches line 10 of 11, not the renew at line 11; the hub's checker names T2 at the same call. That is 1 trace of 100: the generator picks each call at random, so in those 100 traces it reached only 1 accepted requestInput, 0 accepted answers, 0 accepted completes and 4 accepted renews, and most calls end as refusals or reused keys. The stale-holder mutant is caught, but rarely; trace validation as built samples the refusals well and a task's lifecycle poorly.
  - **Not in CI.** CI has no Java and must not get it. A TLC-free check would have to know which α steps the model allows, which is the 5.1 million-edge graph over 144,148 views (about 100 MB even at 20 bytes an edge, fifty times the fixture's budget) or a second implementation of the spec in TypeScript, which would check the code against another reading of the spec and not against the spec. The replay is the CI half of the round trip; trace validation is run locally when `Tasks.tla`, `src/hub/task.ts` or `src/hub/store.ts` changes, at about 0.4 s a trace.
- **What the round trip cannot check.**
  - **Concurrency.** Both directions run one call at a time: `dirtyRead` stays TLC's alone, and B2's racing callers are not covered.
  - **The bounds.** One task (so the claim order is TLC's `design-oldestFirstStarves` and the simulator's, not the replay's), two principals, two keys each, four events, a lease of two ticks. The channel principal and the inbox (`taskWaiting`) are not in the model.
  - **Crash points.** Only before the transaction's first statement and after the answer; the simulator's random run keeps the other statement boundaries and the timer crash.
  - **Selection.** One path per class, not every path; a bug that shows only on a path the classes do not separate is missed by the replay and left to the simulator.
  - **Left open: a generator that follows the lifecycle.** The bounded mode's random calls rarely get a task past `working` (see the counts above). A generator that follows a task's lifecycle (create, claim, request, answer, complete or fail, with waits that let leases lapse) would make trace validation reach the states the stale-holder mutant needs in most traces, not 1 in 100. Not built in B1c.
- **Did it find anything?** One disagreement, the refusal order above, found while mapping the model's refusals onto the code's; it was settled in the spec, not the code. The code passed every path and every trace. The method's value so far is that the model and the code are now known to agree, within the bounds, step by step, and that a change to either that breaks it fails CI.
- **Keep or drop.** Keep the replay in CI: 12 s, and it catches the two lease mutants on correct paths as well as on their counterexamples. Keep trace validation as a local tool, not a gate. Regenerate the fixture when `Tasks.tla` changes or when the code's refusal order changes. Drop the method if keeping α in step with the store costs more than the disagreements it finds.

## 2026-11-22: Effect patched for the seeded budget (BER-2365)

The three liveness failures that the simulator's seeded budget reached (the action contract's entry above) are Effect 4.1.4 bugs, not simulator artifacts, and `patches/effect@4.1.4.patch` fixes all three. Bun applies it on install (`patchedDependencies` in `package.json` and `bun.lock`), so CI gets it too. The owner's go: "We can patch effects bugs if it helps", and "Later we can upstream". With the patch, `withFixedBudget` is gone from `agreement.ts` and from the task hub's simulator, and the seed picks preemption points again: every turn's budget, from 2048 down to 1, is the one `SimRuntime` draws. Each verdict rests on instrumenting the stuck run and on a repro without the simulator's quirks. `SimRuntime` ignores task priorities and the first-in, first-out order Effect documents within one dispatcher, but none of the three needs either.

- **Cause one, the lost interrupt** (`internal/effect.ts`). `forkUnsafe` (5626-5633) schedules a start task that nothing can cancel. When the child is interrupted before that task runs, `interruptUnsafe` (594-613) evaluates the interrupt. Under a budget of 1 the evaluation yields at its first operation (`yieldNow`, 770-779). The start task's `evaluate` then cancels that pending yield (632-636) and runs the body, and the interrupt is lost. Verdict: an Effect bug, reachable with any scheduler whose `shouldYield` is true at an op count of 1; the spec's hand-drained, first-in-first-out scheduler shows it. Fix: the pending start becomes the child's pending yield, so an interrupt that arrives first cancels the start instead.
- **Cause two, the unanswered ping** (`rpc/Utils.ts`). `withRun`, behind `RpcServer.Protocol.make`, decides whether to buffer when a write effect is created (35) but pushes into the buffer when the effect runs (30-33). If `run` replays, clears the buffer and installs its writer in between (44-45), the write lands in a buffer nobody replays. `withRunClient`, behind `RpcClient.Protocol.make`, has the same gap: decided at creation (87-91), pushed at run (75-82). Instrumented, seed 216 showed "replayed 0, installing" and then a push with the writer installed on the server side, and seed 2732 the same on the client side. Verdict: an Effect bug. On Effect's default scheduler, with only the public API, a write created before `run` and run after it is lost. Fix: both buffering writes check for an installed writer when they run and forward to it.
- **Cause three, the empty 500** (`rpc/RpcServer.ts`). `handleRequest` registers the request fiber from inside that fiber's first operation (419-423). Under a budget of 1, `runFork` yields before that operation. The Eof written next sees no fiber (`case "Eof"`, 236-240) and ends the client (`endClient`, 249). McpServer then finds the body empty and answers its "MCP request ended without writing its response" (`ai/McpServer.ts:3052`). Instrumented, seed 1333 logged "Eof client 3 fibers=0", then "endClient 3", and only then the registration. With the budget floored at 2 it never happened on seeds 0 to 2999. Verdict: an Effect bug that only a budget of 1 reaches; Effect's default of 2048 never yields before a fiber's first operation. The repro uses a scheduler that keeps one first-in-first-out queue per fiber, as Effect's contract allows. Unpatched it records `["end"]`; patched, `["send Exit", "end"]`. Fix: `handleRequest` also registers the fiber right after `runFork`. On this main the RPC surface hits it too: there the empty answer reaches the RPC client as a `SchemaError` on its declared failures. With only this hunk applied, the four such seeds below pass, and so does seed 1719, an MCP 500.
