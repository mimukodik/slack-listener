# What we tried while building slack-listener, and what held up

We used one small tool to test how software should be built when coding agents write most of it. Two qualities matter most: an agent should be able to change the code quickly, and the change should keep the behaviour people rely on. This page is the starting point. It covers what we tried and why, how each idea was tested, what we kept or dropped, and what is still open. Every claim links to its evidence.

## The subject

slack-listener wakes a Claude Code session when someone it trusts posts in a Slack channel, so no session has to keep checking. The work is small, but the failures are real ones. A laptop can fall asleep halfway through a delivery. Slack can send the same event twice. The process can crash after posting a reaction but before saving that it did. Each of these has to end with the message delivered once, or flagged as a possible repeat, and never silently lost. The [rules](../RULES.md) say what must always hold. Each rule has a number (R1, R2, …), the owner approves every sentence, and the code is checked against them.

A second tool, the **task hub**, was built beside the listener to track who holds a task and whom it is waiting on. Some of the experiments below ran on both. The language comparison uses the listener only.

Every check above was shown to fail at least once: on a **planted bug**, a deliberate wrong edit that the check should catch. A check that can't fail proves nothing.

**What this doesn't prove:** the fake Slack is a model too, and a mistake shared by the fake and the checker can pass unnoticed. Two planted bugs went unseen in 10,000 runs because the simulated world never reached their code (see [the swarm record](../history/arch-poc/swarm/README.md#two-bugs-no-run-reached)). Live runs on real Slack were done by hand at a few milestones.

## What we dropped

**Swarm testing.** It means switching a random half of the action and fault kinds off for each run ([Groce et al., 2012](https://users.cs.utah.edu/~regehr/papers/swarm12.pdf)). We fixed the bar before measuring: the change would stay only if it caught a planted bug more often in the same time, without the simulator exercising less of the code. It failed. With equal run time, 18 of 19 planted bugs were caught less often, and most coverage counters fell. Our hard bugs need several behaviours in the same run, and switching kinds off removes them. [The experiment, numbers and raw data](../history/arch-poc/swarm/README.md).

## What is still open

**Which language makes the next correct change cheapest for an agent?** The listener works in TypeScript on [Effect](https://effect.website/). Agents are building the same listener in Rust and in Zig. Once all three pass one common acceptance gate, fresh agents get the same unseen maintenance tasks, and we measure time per accepted change and correctness. Nothing has been scored yet. [The comparison, its status and its open design questions](listener/README.md).

**Experiments planned before the pause:**

- Hegel as a shrinker, to cut a failing run down to a short, readable case.
- Fault knobs and clock jumps.
- Liveness checks with concurrent callers.
- Browser-level checks of a future UI.

These and the work order at the pause are in [the history of the first phase](../history/arch-poc/README.md).
