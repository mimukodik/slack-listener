# Principles

How slack-listener is designed, written and tested. It follows [Tiger Style](https://github.com/tigerbeetle/tigerbeetle/blob/main/docs/TIGER_STYLE.md) and deterministic simulation testing as TigerBeetle, FoundationDB and Antithesis practise it, carried over to TypeScript and [Effect](https://effect.website). [RULES.md](RULES.md) says what the tool does; this file says how it is built. Each principle has a stable id, how it is enforced, and whether the code holds it today. A principle the code does not yet hold is a target, and the work towards it is planned, not hidden.

## Manifesto

**Safety, then performance, then developer experience, in that order.** A message that should not reach a session must never reach it, and one that should must not be lost. Only then does speed count, and only then comfort.

**The simulator runs the program, not a model of it.** Production and simulation start the same Effect program. The simulator swaps only the world underneath: the clock, the scheduler, randomness, the network, the socket, the session and the disk. Whatever runs only in production is untested.

**Every run is a seed.** All nondeterminism comes from one stream of choices. The same choices give the same run, down to the order of fibers and the millisecond of every timer, so a failure is found once and replayed forever.

**Assertions are the oracle.** The code states what must be true and what must never happen, and stops when either breaks. The simulator multiplies every assertion by millions of executions; a missing assertion is a bug the simulator cannot see.

**Everything has a limit.** Every queue, cache, retry and wait is bounded, and every request has a deadline. Unbounded is a bug that has not happened yet.

## Determinism

| Id                           | Principle                                                                                                                                                                                                                                                          | Enforced by                                                                                                                                                                                                                                                             | Holds today                                                             |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| `world-through-services`     | Application code reaches the outside world only through Effect services: `Clock`, `Random`, the `Scheduler`, `HttpClient`, `Socket`, `Stdio`, `FileSystem`. It never calls `Date.now`, `Math.random`, timers, `fetch`, `WebSocket`, `node:fs` or `process` itself. | `no-restricted-globals`, `-properties` and `-imports` in [.oxlintrc.json](.oxlintrc.json); the simulator's tripwire in `src/sim/host.ts`, which throws on a real timer. Lint cannot tell a bare `new Date()` from a pure `new Date(ms)`; the tripwire catches the first | pure modules only; the shell still uses Node directly                   |
| `simulator-runs-the-program` | The simulator starts the same program as `main.ts` and replaces only the tools under it: the `fetch` function, the WebSocket constructor, stdio, the disk, the clock, the scheduler and the random seed. No application logic exists only in the simulator.        | one program entry shared by `main.ts` and the simulator; review                                                                                                                                                                                                         | no: the simulator drives the core with its own interpreter              |
| `one-seed-one-run`           | Every decision the simulator makes, including which fiber runs next and when an answer arrives, comes from one stream of choices. A seed or a recorded stream replays a run exactly.                                                                               | `src/sim/runtime.spec.ts`: 200 seeds, half with a crash, each run twice and the traces compared; the seed must change the run                                                                                                                                           | for the simulation runtime: yes; the application runs on it from step 3 |
| `fakes-are-models`           | A fake is a model of an outside system and is kept honest by recordings. A surprise from real Slack becomes a recorded fixture first and a change to the fake second.                                                                                              | the conformance tests in `src/sim/conformance`                                                                                                                                                                                                                          | yes, for two event kinds                                                |
| `faults-are-first-class`     | Every operation is simulated failing in each way it can: slow, failing, never answering, duplicated, reordered, disconnected, crashed without cleanup and restarted from disk, put to sleep. A failure mode the simulator does not produce is listed as untested.  | coverage counters that must be non-zero                                                                                                                                                                                                                                 | partly: no hangs, no crash inside the shell                             |
| `shrink-the-run`             | A failing run shrinks to a minimal run: fewer actions, fewer faults, simpler choices. The choice 0 is always the simplest one: no fault, the shortest delay.                                                                                                       | a shrink test on a planted bug                                                                                                                                                                                                                                          | no: today the seed is shrunk, not the run                               |

## Safety

| Id                      | Principle                                                                                                                                                                                                                       | Enforced by                                                                                                                                                                                                                                                                                                                                                                                           | Holds today                                                                                      |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `assert-the-invariants` | Assert arguments, results and invariants, on average two per function. Pair them: check a property where it is written and where it is read. Assert what must not happen as well as what must. Corrupt state stops the process. | a lint rule that counts assertions per function (planned)                                                                                                                                                                                                                                                                                                                                             | no: assertions live in the core's `step` only                                                    |
| `check-every-step`      | Safety properties are checked after every simulated step, progress properties at the end of a run. Two controls, a build that delivers nothing and one that delivers everything, must fail.                                     | `src/sim/sim.spec.ts`                                                                                                                                                                                                                                                                                                                                                                                 | yes                                                                                              |
| `limit-everything`      | Every loop, queue, cache, retry and wait has an explicit bound in configuration, and every in-flight request has a deadline.                                                                                                    | review; simulator checks such as R8                                                                                                                                                                                                                                                                                                                                                                   | no: in-flight fetches and deliveries have no deadline, and the thread-starter cache is unbounded |
| `simple-control-flow`   | No recursion. Functions of at most 70 lines: control flow in the parent, non-branching work in pure helpers. Nesting at most three deep, at most five parameters. Every `switch` over a union is exhaustive.                    | `max-depth`, `max-params`, `max-nested-callbacks`, `switch-exhaustiveness-check`; `max-lines-per-function` once the long functions are split                                                                                                                                                                                                                                                          | partly: four functions are longer than 70 lines                                                  |
| `failure-is-typed`      | Every operation states how it can fail, as a typed error named in the domain's language. A failure is handled at the level that can decide about it; an unexpected one stops the process loudly; nothing is swallowed.          | Effect's typed errors, and Effect's rules in the patched `tsrs` set in tsconfig.json (`floatingEffect`, `globalErrorInEffectFailure`, `effectTryWithoutCatch`, `tryCatchInEffectGen` and the rest); `no-floating-promises`, `no-misused-promises`, `only-throw-error`, `prefer-promise-reject-errors`, `use-unknown-in-catch-callback-variable`, `promise-function-async`; `noUncheckedIndexedAccess` | yes                                                                                              |
| `decisions-are-pure`    | Business decisions live in side-effect-free functions over plain data: `step(state, event, now)` returns the new state and the effects. The program around it runs the effects.                                                 | the determinism bans, strictest on the core's files                                                                                                                                                                                                                                                                                                                                                   | yes                                                                                              |

## Working

| Id                              | Principle                                                                                                                                                                                                          | Enforced by                                                               | Holds today                      |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------- | -------------------------------- |
| `rules-are-the-source`          | [RULES.md](RULES.md) is the source of truth for behaviour, with numbered rules whose ids are never reused. A rule is not edited to make a test pass.                                                               | review; [DECISIONS.md](DECISIONS.md) logs every change with its direction | yes                              |
| `guardrails-are-proven`         | Every check, lint rule and test is shown to catch an example of the failure it exists for, on a deliberately broken build, before it is trusted.                                                                   | the pull request's evidence                                               | yes                              |
| `structure-and-behaviour-apart` | A change either restructures without changing behaviour or changes behaviour, never both. A restructure lands first, on its own.                                                                                   | review                                                                    | yes                              |
| `evidence-on-the-exact-version` | Lint, tests, the simulator and the exhaustive pass run on the exact commit that lands, and an independent review accepts that commit.                                                                              | CI on every pull request; the merge rule                                  | yes                              |
| `few-dependencies`              | Every dependency earns its place: Effect for the program, fast-check for generation and shrinking, the rest is tooling. A tool that fits is used unchanged and stays replaceable: its rules live in configuration. | review                                                                    | yes                              |
| `names-carry-units`             | Names are whole words, and units come last, most significant first: `timeoutMs`, `latencyMsMax`, `catchUpWindowMs`.                                                                                                | review                                                                    | mostly                           |
| `performance-is-budgeted`       | Speed is estimated before it is built and measured after. The simulator has a budget too: a run costs well under a millisecond, so millions of runs fit into CI and a night.                                       | the simulator prints its time per run                                     | measured, not yet budgeted in CI |

Where a principle and a shortcut conflict, the principle wins or the conflict is raised; it is never worked around silently. A principle changes by a pull request that says why, recorded in [DECISIONS.md](DECISIONS.md).
